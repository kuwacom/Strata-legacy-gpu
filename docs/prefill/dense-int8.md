# dense 射影を int8 常駐 + 素の DP4A GEMM にする（不採用）

取得日: 2026-11-11。P40 1 枚（`strata:fork-dense8`、分岐 `perf/dense-int8`、main = e1d8b20f）。
計測は 128K 1 アーム（137,344 tokens）。比較の基準は v7（GPU timeline 182,758 ms）。

## 結論

**不採用。** 128K の GPU timeline は 182,758 -> **212,379 ms（+16.2%）**、`gdn` は 26,324 -> **48,148 ms**、
`qsa proj` は 12,279 -> **20,287 ms**。他位相は ±25 ms 以内で動かない（形で門を作ったので、負けた形には
一切触れていない）。品質は落ちない（QA 128K 8/8、needle 24K/32K/128K すべて found）ので、**速度だけで負け**。

## 何を作ったか

- `src/prefill/dense_i8.cu` / `include/strata/prefill/dense_i8.hpp`（`STRATA_DENSE_I8=1`、既定オフ）
  - 重み [N, K] を呼び出しごとに 1 度だけ per-32 スケールの int8（`q8`）へ展開する（`dequant_f16` で FP16 に
    開いてから 32 値ごとに最大絶対値 / 127 で丸める。4 bit -> 8 bit の取り直しで誤差は元の 1 段の 3% 程度）
  - 活性も同じ形式へ量子化し（`quantize_kernel`）、ブロック 128 行 x 64 トークン、1 スレッド 8 行 x 4 トークン、
    K チャンク 64 値の DP4A GEMM で掛ける（共有メモリの行ストライドを 17 ワードにして bank の重なりを回避）
  - 32 値ごとに int32 の和を fp32 のスケールで畳む（`fmaf((float) sum, w_scale * x_scale, acc)`）
- `src/prefill/gemm.cu`: `Gemm::native` の MMQ 分岐の直前に `dense_i8::run` を挿す（beta 0、ldx == K、
  `N >= 4 K` かつ `N >= 8192` の形だけ）。
- `src/prefill/dense_i8_bench.cu`: 形・型ごとの速度と、FP16 の厳密な積との誤差、および**このカードの DP4A の
  上限**（メモリを触らないループ）を測る。`--peak` で上限だけ。

## 2. なぜ負けたか（実測）

- `--peak`（メモリを触らない 16 本の独立 dp4a 鎖）: **35.5 TFLOPS**（17.7 TMAC/s）。P40 の DP4A の上限は
  仕様どおり 47 TOPS の 75% まで出る。32 値ごとの畳み込みを足しても 36.2 TFLOPS で、**畳み込みはほぼ無料**。
- ところが本 GEMM は 6.1 TFLOPS = 上限の **17%**。SASS は 1 チャンク（2 グループ）あたり
  `IDP.4A` 512 + `LDS.U.32` 192 + `I2F/FMUL/FFMA` 192 + staging 32 で、**dp4a 1 回あたり 1.9 命令**。
  それでも命令発行の上限（4/cycle）では 273 MAC/cycle 出るはずで、実測は 67 MAC/cycle。つまり
  **共有メモリのレイテンシで止まっている**（16 ワープ常駐でも IPC 1.0/4）。4 バイトのスカラー LDS が
  96 回/32 値あり、ロード 12 発ごとに 32 dp4a が依存する形なので、次の kk の先読みが要る。
- 一方 llama.cpp の MMQ は同じ DP4A で本番 10〜15 TFLOPS（上限の 30〜45%）。**重みタイルの unpack は
  J=64 トークンで十分に償却されており**、「64 トークンごとに unpack し直すのが損」という見立ては
  実測で裏付けられなかった（unpack を 1 回にしても、GEMM 側が 2.4 倍遅ければ意味がない）。

## 4. 品質（不採用なので参考値）

- needle 24K/50%: found、32K/50%: found、32K/90%: found、128K/50%: found、128K/90%: found
- QA 128K: **8/8**
- FP16 の厳密な積に対する RMS 相対誤差: IQ4_XS 0.0039〜0.0040、Q3_K 0.0059（重みの 4 bit -> 8 bit の
  取り直しぶん。活性の量子化は MMQ と同じ規則）

## 5. 次に試すなら

1. この GEMM を作り込むなら、まず 16 バイトの共有メモリ読み（int4）と次の kk の先読みで **IPC を 1 -> 2.5**
   に上げる。ただしそれでも上限は 35 TFLOPS で、MMQ の 10〜15 を抜けるには 45% 以上が要る
2. 形で勝てる場所を探すなら、まず**現行の経路を正しく測る**（このベンチは MMQ を立てずに回した）。
   `STRATA_DENSE_MMQ=0/1` x `STRATA_DENSE_F32=0/1` の 4 通りを同じ形で並べれば、どの形がどの経路で
   何 TFLOPS かが確定する
3. int8 の積和そのものを減らす方が筋が良い: 射影の入力を共有する（`mixed_h` を 1 層 1 回だけ量子化して
   qkv / gate / k / v / q で使い回す）だけで、射影 1 本あたり活性 T x K の書き戻しが 1 回減る
