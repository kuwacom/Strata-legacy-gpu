# Qwen3.8-Flash-Next IQ3_XXS の 512K context（Tesla P40 24GB + RAM 98GiB）

## 結論

- `--max-context 524288` で起動し、短いプロンプト・112K・327K のプロンプトで応答が返った（本番 image `ghcr.io/niko1221/strata:0.2.7-cuda12`、engine 0.1.52、int8 KV、`--kv-resident 32768`、`--rope-scaling yarn --rope-scale 2`）
- KV は 1 トークンあたり 12,672 B（int8、QSA 12 層）。512K で 6.19 GiB。このうち VRAM に置くのは 32,768 cells 分の 0.39 GiB だけで、残りは pinned RAM。KV を SSD に退避する経路はない（SSD 退避量 0）
- prefill は 4K/24K で 459/493 tok/s（128K の基準 450-480 と同等）、112K で 444 tok/s、327K で 351 tok/s。decode は 40-46 tok/s（基準 45-50 の範囲内）
- 全 524,288 トークンのプロンプト投入は未実施（GPU ロック 1 ブロック 60 分の制約と、手元コーパスが約 379K トークンしかないため。理由は「未確認・リスク」に書く）

## KV の 1 トークンあたりのバイト数

式はコードから取った。1 cell = 1 トークン × 1 QSA 層。

int8（`include/strata/kernels/kv_q8.hpp:25-27`）:

```
bytes/cell = n_head_kv * head_dim * 2                      # K int8 + V int8
           + n_head_kv * (head_dim / 64) * 2 * 2           # K/V の fp16 scale（64 値ごと）
           = 2 * 256 * 2 + 2 * 4 * 2 * 2
           = 1024 + 32 = 1056 B
```

q4_0（`include/strata/kernels/kv_q4.hpp:33-38`、`block_q4_0` は 32 値で 18 B）:

```
bytes/cell = n_head_kv * (head_dim / 32) * 18 * 2
           = 2 * 8 * 18 * 2 = 576 B
```

k8v4（K int8 + 回転済み Q4_0 V、`src/core/layer.cpp:757-767` の hybrid 分岐）:

```
bytes/cell = 2 * 256          # K int8
           + 2 * 4 * 2        # K scale
           + 2 * 8 * 18       # V q4_0
           = 512 + 16 + 288 = 816 B
```

fp16（`src/core/layer.cpp:766`）: `2 * 256 * 2 * 2 = 2048 B`

QSA 12 層ぶんの合計と、512K（524,288 cells）での総量:

| KV 形式 | 1 cell | 1 トークン（12 層） | 512K 合計 | 備考 |
| --- | ---: | ---: | ---: | --- |
| int8 | 1,056 B | 12,672 B (12.375 KiB) | 6,643,777,536 B = 6.19 GiB | 採用 |
| q4_0 | 576 B | 6,912 B (6.75 KiB) | 3,623,878,656 B = 3.38 GiB | 未検証 |
| k8v4 | 816 B | 9,792 B (9.5625 KiB) | 5,134,077,952 B = 4.78 GiB | 未検証 |
| fp16 | 2,048 B | 24,576 B (24 KiB) | 12,884,901,888 B = 12.0 GiB | 未検証 |

補足: 起動ログの実測は `KV streaming: 32768 of 524288 cells per QSA layer in VRAM, the K/V in 6.19 GiB of pinned RAM` で、上の 6.19 GiB と一致する。engine のヘルプも int8 を 1,056 B/cell、k8v4 を 816 B/cell と書いている（`src/program/generate.cpp:1046-1048`）。

## 512K のメモリ内訳

### VRAM（24 GiB）

| 項目 | 512K | 128K（比較） | 根拠 |
| --- | ---: | ---: | --- |
| KV の VRAM 分（32,768 cells × 12 層） | 0.39 GiB | 0.39 GiB | `src/core/layer.cpp:738-755` の mode 1、`kv_pool_bytes` |
| indexer pooled（`max_cells/4+2` 行 × 128 float × 12 層） | 0.75 GiB | 0.19 GiB | `src/core/layer.cpp:788-806` の pooled 行 |
| RoPE cos/sin テーブル（1 枚を 12 層で共有） | 128 MiB | 32 MiB | `src/core/layer.cpp:952-970`、`max_cells * 32 * 4 * 2` |
| page table（131,072 ページ × 4 B × 12 層） | 6 MiB | 1.5 MiB | `src/core/layer.cpp:794` |
| KV residency map（8,192 slots × 20 B + ctl × 12 層） | 約 2 MiB | 同 | `include/strata/kernels/kv_stream.hpp:80` |
| GDN state（36 層） | 112 MiB | 112 MiB | `src/core/session.cpp:35-40` |
| cell_scores（max_cells × float） | 2 MiB | 0.5 MiB | `src/core/layer.cpp:1029-1041` |
| モデル重み（dense/native/head/MTP） | 約 5.5 GiB | 約 5.5 GiB | 起動ログ（expert cache 以外の残り） |
| expert cache（実測） | 16.73 GiB（10,315 slots） | 17.40 GiB（10,720 slots） | 起動ログ |

512K で KV 関連の VRAM は 128K より約 0.68 GiB 増える。そのぶん expert cache が 405 slots 減る（405 × 1.66 MiB = 0.66 GiB）。起動ログの 10,720 -> 10,315 と整合する。

### RAM（98 GiB）

| 項目 | 512K（実測/推定） | 根拠 |
| --- | ---: | --- |
| KV の pinned host copy（全 524,288 cells × 12 層） | 6.19 GiB | `src/core/layer.cpp:917-947`。`pages * kv_block_bytes + 1024` を層ごとに `cudaHostRegister` |
| expert arena（pack の専門家を丸ごと pinned） | 39.97 GiB | 起動ログ `loaded 39.97 GiB at 0.53 GiB/s` |
| PLE n-gram テーブル（`--ple-io ram`） | 26.8 GiB（28.8 GB） | 起動ログ `PLE table locked in RAM` |
| conversation cache | 7.0 GiB（7,168 MiB） | 起動ログ。空き RAM から自動で決まる |
| engine/serve の作業領域 | 約 2 GiB（推定） | 差分 |
| 合計（idle 実測 RSS） | 77 GiB（MemAvailable 20 GiB） | `free` 実測 |
| 327K プロンプト中の実測 | 84.7 GiB（MemAvailable 15.9 GiB） | `free` 実測 |

### SSD

| 項目 | 512K |
| --- | ---: |
| KV の SSD 退避 | 0 B |

KV streaming は VRAM と pinned RAM の間だけで動く（`src/kernels/cuda/kv_stream.cu` に file/SSD の経路はない）。SSD に出るのは expert pack と PLE テーブルの読み出しだけで、どちらも読み取り専用で RAM に pin される。

## 512K を成立させているコード経路

- **max-context のクランプはない**。`src/program/generate.cpp:4405-4408` は `2^31` 未満かどうかだけを見る。524,288 は通り、起動ログも `--max-context 524288` をそのまま受けている。
- **rope scaling**。既定は `RopeScaling::None` で、`orig_ctx` の既定は 262,144（`include/strata/kernels/rope_scaling.hpp:66-71`）。`--rope-scaling yarn --rope-scale 2` で `freq_scale = 0.5`、`mscale = 1 + 0.1 * ln(2) = 1.069315` になり、cos/sin テーブルに焼き込まれる（`src/core/layer.cpp:952-970`）。起動ログ: `rope scaling yarn, factor 2 (freq_scale 0.5, base 1e+07, mscale 1.069315), --max-context 524288 against a trained context of 262144`。テーブルは `max_cells` 行ぶん作られるので 512K でも足りる。
- **paging / streaming**。`kv_plan`（`src/core/layer.cpp:738-755`）は `--kv-resident > 0` かつ resident ページ数 < 全ページ数のとき mode 1（streamed）を選ぶ。512K では pages = 524288 / 4 = 131,072、resident = 32,768 / 4 = 8,192 ページ。host copy は全 131,072 ページぶんを起動時に pin する（`src/core/layer.cpp:917-947`）。attention は選択されたブロックだけを VRAM に引き上げる。実測の VRAM ヒット率は 24K で 97.4%、112K で 92.5%、327K で 89.3% で、RAM からの読みは 206-462 MiB だった。
- **確保は起動時一括**。既定では `--max-context` ぶんの KV を起動時に確保する（`src/program/generate.cpp:1051-1053`）。`--kv-grow` は VMM で必要ぶんだけ map する別方式だが、`src/program/generate.cpp:6659-6672` の条件（1 GPU、profile あり、KV 全量が VRAM、streaming なし）を満たす必要があり、`--kv-resident` とは併用できない。今回は起動時一括を採用した。

## 候補構成

| 構成 | KV の VRAM | KV の RAM | 推定 expert slots | 状態 |
| --- | ---: | ---: | ---: | --- |
| A: int8 + `--kv-resident 32768`（採用） | 0.39 GiB | 6.19 GiB | 10,315（実測） | 検証済み |
| B: q4_0 + `--kv-resident 32768` | 0.21 GiB | 3.38 GiB | 約 10,400（推定） | 未検証 |
| C: int8 全量 VRAM（`--kv-resident 0`） | 6.19 GiB | 0 | 約 6,800（推定） | 未検証 |
| D: q4_0 全量 VRAM | 3.38 GiB | 0 | 約 8,500（推定） | 未検証 |
| E: int8 + `--kv-resident 65536` | 0.77 GiB | 6.19 GiB | 約 10,100（推定） | 未検証 |

A を採用した理由: 本番 128K と同じ KV 形式で品質差を持ち込まず、RAM も 98 GiB に収まる（idle で 20 GiB 余る）。B は RAM を 2.8 GiB 節約するが VRAM の利得は約 110 slots しかない。C/D は pinned RAM が不要になる代わりに expert cache が大きく減り、decode のヒット率が落ちる見込み。

`--vram-reserve-mib` は既定の 700 MiB のままにした。327K プロンプト中に VRAM 空きが 273 MiB まで減り、engine が `--vram-reserve-mib 896` を勧める警告を出した（`#2065`）。余裕を持たせるなら 896 を足す（expert slots が約 120 減る）。

## 実機検証

条件: 本番コンテナを停止し、同じ image・同じデータボリューム `compose_strata-data` で別コンテナを起動。engine 引数は本番と同じで、`--max-context 524288 --kv int8 --kv-resident 32768 --rope-scaling yarn --rope-scale 2 --ple-io ram --prefill auto --spec 4 --mtp` を追加した。

### 起動

- 起動成功。engine 開始 16:12:52、server ready 16:15:02.8 -> 起動時間 130.8 秒
- `KV streaming: 32768 of 524288 cells per QSA layer in VRAM, the K/V in 6.19 GiB of pinned RAM`
- `expert cache 10315 slots, 16.73 GiB of VRAM`
- `544 MiB of VRAM free with everything loaded`
- `conversation cache sized from the free RAM: 7168 MiB`
- idle 時: VRAM 23,895 MiB 使用 / 544 MiB 空き、RAM 77 GiB 使用 / MemAvailable 20 GiB
- 327K プロンプト中: VRAM 24,167 MiB 使用 / 273 MiB 空き、RAM 84.7 GiB 使用 / MemAvailable 15.9 GiB
- 起動時に `the expert arena needs 39.97 GiB of RAM but 21.65 GiB is available` の警告が出たが、page cache を追い出して 39.97 GiB を pin でき、起動は完了した（本番 128K でも同じ警告が出ている）

## 未確認・リスク

- **全 524,288 トークンのプロンプトは未実施**。理由は 2 つ: GPU ロックの 1 ブロック 60 分に収まらない見込み（327K の prefill が 933 秒、512K は推定 1,150 秒以上）、手元の `~/Strata/docs/*.md` が約 379K トークンぶんしかなく、繰り返しで水増しすると品質評価の意味が薄い。max-context 524288 の確保自体は起動ログで確認済み。
- **YaRN は experimental**。docs も「512K の品質は未評価」と書いている。今回は「応答が返る」「クラッシュしない」だけを見ており、長文 recall や一貫性は測っていない。
- **VRAM 余裕が小さい**。327K 中に空き 273 MiB。engine 自身が `--vram-reserve-mib 896` を推奨している。896 を足すと expert slots が約 120 減る。
- **P40 の温度**。docs/OLDER_GPUS.md にある通り 89 C で thermal slowdown が入る。今回の測定は温度を揃えていないので、A/B の厳密比較には使えない。
- **RAM の余裕**。idle で 20 GiB、327K 中で 15.9 GiB。512K のプロンプトでは conversation cache と prompt buffer がさらに増える可能性がある。`--conversation-cache-mib` を絞る余地がある。
- q4_0/k8v4/全量 VRAM の各候補は起動していない（推定値のみ）。
- `--kv-grow` は `--kv-resident` と併用できない（コード条件）。512K で streaming をやめる場合の選択肢。

## 再現コマンド

```sh
# GPU ロック
mkdir /tmp/strata-gpu.lock && echo "ctx512 $(date -Is)" > /tmp/strata-gpu.lock/owner

# 本番を止める
sudo docker stop strata

# 同じ image・同じボリュームで検証コンテナ
sudo docker run -d --name strata-ctx512 --gpus all -p 127.0.0.1:8080:8080 \
  -v compose_strata-data:/data --ulimit memlock=-1:-1 --shm-size=2gb \
  -e HOME=/data/home -e XDG_STATE_HOME=/data/state -e XDG_CONFIG_HOME=/data/config \
  -e STRATA_IN_DOCKER=1 -e STRATA_COMPONENTS_DIR=/opt/strata/components \
  -e STRATA_DENSE_F32=1 -e NVIDIA_VISIBLE_DEVICES=all \
  -e NVIDIA_DRIVER_CAPABILITIES=compute,utility \
  --entrypoint /usr/bin/tini ghcr.io/niko1221/strata:0.2.7-cuda12 -- sleep infinity

# 本番の docker.json から検証用 config を作る（~/work/results/ctx512/mkconfig.py）
sudo docker cp ~/work/results/ctx512/mkconfig.py strata-ctx512:/tmp/mkconfig.py
sudo docker exec -e CTX=524288 -e KV=int8 -e RESIDENT=32768 \
  strata-ctx512 /opt/strata/terminal/python/bin/python3 /tmp/mkconfig.py

# engine_ready_s は docker.json の値をそのまま使う（0 は不可）
sudo docker exec strata-ctx512 sh -c \
  'sed -i "s/\"engine_ready_s\": 0/\"engine_ready_s\": 946/" /tmp/ctx512.json'

# serve
sudo docker exec -d strata-ctx512 sh -c \
  'cd /opt/strata/terminal && exec /opt/strata/terminal/python/bin/python3 -m serve.server \
   --engine strata --config /tmp/ctx512.json --host 0.0.0.0 --port 8080 --parallel 1 \
   > /tmp/serve.out 2>&1'

# ベンチ（API キーは表示しない）
export STRATA_API_KEY=$(sudo docker exec strata-ctx512 \
  /opt/strata/terminal/bin/strata launch --show-key --preset docker 2>/dev/null | tail -1)
BENCH_SEED=42 python3 ~/bench.py 4000,24000 1 256 code,prose
BENCH_SEED=42 python3 ~/bench.py 100000 1 128 prose
python3 ~/work/results/ctx512/longbench.py 1080000 8    # 327K 相当

# 後片付けと本番復元
sudo docker rm -f strata-ctx512
cp ~/opt-work/prod.env ~/Strata/docker/compose/.env
cd ~/Strata/docker/compose && sudo docker compose \
  -f docker-compose.nvidia.yml -f docker-compose.override.yml up -d --force-recreate
sudo docker inspect -f '{{.State.Health.Status}}' strata
rm -rf /tmp/strata-gpu.lock
```
