# S_K MoE (gu/dn) の occupancy 実験 (launch_bounds(128,4) / 重み先行ロード)

調査日: 2026-11-25 / 対象: `~/work/ink` branch `perf/ink-sk-occ` (base `perf/ink-sf4-launch` HEAD `d59c0373a`、実験コミット `b872a8f81`) / バイナリ sha256 `45c344fb…` / Tesla P40 (sm_61) 単機 / SQ-10 / 32K prefill (chunk 512、fp16、dspark、`STRATA_INK_PF_TILE=1 STRATA_INK_PROF=2`)。GPU は共用ロック内で使い、本番は復旧済み (healthy、`.env` sha256 `(省略)` 不変、両ロック解放)

## 結論

- **実験 A (occupancy) は成立**。`__launch_bounds__(128,4)` で REG 160 -> **128**、spill は実質無し (gu S2_K / dn は STACK 0、gu S3_K のみ STACK 8 B)。**3 -> 4 CTA/SM (12 -> 16 warp)** になり、**gu(sk) 609.21 -> 567.08 / dn(sk) 358.13 -> 308.64 / 合計 967.34 -> 875.72 ms/step (−91.62 ms、−9.5%)**、**prefill 242.3 -> 254.2 ppts (+4.9%)**
- **実験 B (重みの 1 sub-block 先行ロード) は不成立**。REG 150/160 で 3 CTA/SM のまま、**合計 1,010.33 ms/step (+4.4%)**、**prefill 238.4 ppts (−1.6%)**。先行ロードでレジスタとアドレス計算が増える割に MLP が足りず、素直に遅くなった
- **A と B は排他**。B の REG は 150-160 で 128 を超えるため 4 CTA/SM と両立しない (測定でも B は 3 CTA/SM のままで、A の利得と重ならない)
- 数値結果は変えていない: 同一プロセス内で gu の `h_f32` と dn の `y_pair` を **20/20 visit で bit 一致** (OCC=1 / OCC=2 の両方、S2_K / S3_K の両形式)
- 同一アームの重複 (OCC=0 を 2 回) の差は gu +0.13% / dn +0.03% / prefill +0.33%。A の差 (−9.5% / +4.9%) はそれを大きく超える
- 判定: **合格条件 (bit 一致 + gu(sk)+dn(sk) の短縮 + prefill 向上) は OCC=1 で満たす**

## 解釈

- **A が効いた理由は warp 数**。3 -> 4 CTA/SM = 12 -> 16 warp (+33%) で、重みと活性の load を重ねる余地が増えた。ただし S_K の短縮は −9.5% で warp 増加分には届かない。まだ stall が残っている (律速は occupancy だけではない)
- **dn の方が効いた** (−13.8% vs gu −6.9%)。dn は 1 CTA あたりの重みが約半分 (pair 32 x 9 block x 102 B = 29.4 KB、gu は 58.75 KB) で、計算に対する load の比率が高く latency 支配が強い。occupancy を上げる効果が大きいという仮説と整合する
- **B が負けた理由は MLP が増えないままコストだけ増えたこと**。1 sub-block 先読みでは同時に飛ぶ load が 2 -> 4 本に増えるだけ (1 warp あたり 32 -> 64 B) で、128 reg に収まらないため warp 数は 12 のまま。先行ロードの `mov` 8 個/sub-block とアドレス計算、レジスタ圧によるスケジューリング自由度の低下が上回った
- **次の律速は依然として latency**。S_K 875.7 ms は 36.4 GB/s で、DRAM floor (~92 ms) の 9.5 倍。活性側は 1 CTA あたり 16 token x 36 block x 80 B = 46 KB (論理量) を 4 warp がそれぞれ読むため L1 要求は ~295 KB/CTA 反復になり、重み 58.75 KB の 5 倍。こちらは L1/L2 依存の連鎖で、occupancy をこれ以上上げるには REG<=102 (5 CTA/SM) が必要だが spill 無しでは無理

## 逸脱・注意

- **検証コードは 2 回ビルドしている**。bit 比較入りのバイナリ (8,827,192 B) で検証し、検証コードを削除して再ビルドしたバイナリ (8,820,752 B、sha `45c344fb…`) で性能を測った。両者は検証ブロック以外同一ソース
- **バイナリが 6,558,248 -> 8,820,752 B (+2.26 MB) に増えた**。OCC=1/2 のカーネルを 7 形式 x 3 MAX_M 分インスタンス化しているため。SQ-10 の S_K は S2_K / S3_K だけなので、本線に入れるなら形式を絞るか OCC を 1 本に固定して削れる
- `STRATA_INK_SK_OCC` は M<=32 (MAX_M=4) と M==1 の経路にも効く。**MAX_M=1 の REG は 76/80 -> 88/90 になるので decode の CTA/SM は 6 -> 5 に落ちる** (未測定の潜在的後退)。今回の decode 値 (25.1 -> 25.7 tps) は run 間差 ±1.6% のノイズに埋もれており、判断材料にならない。**本線採用時は M<=32/M==1 を従来のままにする (MAX_M==16 のときだけ OCC を効かせる) のが安全**
- 実 occupancy は ncu で確認していない (未実行)。CTA/SM は REG からの計算値 (65,536 reg/SM、256 reg/warp 粒度は sm_61 のドキュメント値)
- OCC=1 の `gu_sk_fmt_occ<S3_K,16,1>` だけ STACK 8 B が出る (2 word の spill)。LOCAL は 0 で、性能は gu 全体で −6.9% 出ているため無効化要因ではないと判断した
- 測定は各アーム 1 本 (ばらつき確認用に OCC=0 のみ 2 本)。位相の再現性 0.1-0.3% に対し差が 4.4-9.5% なので判定には足る
- 32K prefill の 1 アームは約 4 分 (モデルロード + 135 s)。4 アームで 14 分、本番の停止/復帰を含めて約 19 分

## 次の提案

1. **OCC=1 を本線候補にする**。`STRATA_INK_SK_OCC=1` の内容を既定にし、MAX_M==16 だけに限定、形式を S2_K / S3_K に絞ってバイナリ増を抑える。128K / 512K でも同じ比率が出るか 1 本ずつ確認する
2. **5 CTA/SM は狙わない**。REG<=102 が必要で、`ag[16]+au[16]` (32) + `xp[16]` (32) だけで 64 reg を使うため spill 無しでは不可能。occupancy 路線はここで打ち止め
3. **次は活性側の traffic を減らす**。`MAX_M=16` は活性をグローバルから直接読む (`SM_M=1`)。16 token x 36 block x 80 B = 46 KB を shared に置けば CTA 内の再読みが L1 から shared に変わり、`xp[16]` の 32 reg も消える (shared は 0 B なので 4 CTA/SM でも 46 KB x 4 = 184 KB が上限を超える -> 8 token ずつ 2 回に分けて 23 KB x 4 = 92 KB が現実的)。REG も下がるので 5 CTA/SM の目も出る
4. 実験 B の形を変えるなら「重みを shared に 2 段ステージ」({32 feature x 2 行 x 102 B} = 6.5 KB/stage)。ただし sm_61 に cp.async が無いので、レジスタ経由の store になり先行ロードと同じ制約を受ける
5. SF4 側 (656 ms) の occupancy は 5 CTA/SM と足りているので、次は 72 CTA/層 = 2.4 CTA/SM の起動形状 (1 launch で全 SF4 expert をまとめる) の方
